# 000-k8s · Baseline shape on Kubernetes (kind)

**Setup.** `deploy/k8s/overlays/000-k8s` on the kind cluster `lab`: api 0.5 CPU / 128 MiB, pg pool 10; db 1 CPU / 256 MiB; loadgen target `k8s` (NodePort 31000 through the kind node container). Observer: the api's own cgroup `/stats`. Raw: `results/raw/000-k8s-open-<op>-<rps>.json` (git-ignored), first-pass read 5000 in `results/raw/000-k8s-pass1-open-read-5000.json`; machine-readable: `results/000-k8s.json`.

**Protocol.** loadgen open model, 20 s per run, in-flight cap 10 000; reset and 5 s idle before each run; `/status?target=` and the raw `/stats` sampled every 2 s from t = 4 s. Peak CPU and commits/s come from consecutive raw counter samples; throttled = api `nr_throttled` added during the run, up to the last sample before a kill. Latency in ms. Each run starts on an api pod with 0 restarts (a pod left in CrashLoopBackOff by the previous kill is replaced with `rollout restart`) and only after 20 clean rounds of 5 `/health` probes through NodePort 31000: after an OOM kill the NodePort reset connections for up to ~100 s while the pod was Ready. Restarts = api container `restartCount` after the run (all OOMKilled, exit 137). Achieved rps counts every completed request, errors included; errors carry no HTTP status.

**Cause rules** (the baseline's, written out): api restarted during the run → *memory ceiling*, failed; else peak memory ≥ 127 MiB with drops or errors → *memory ceiling*, failed; else drops or errors → *saturated*, failed; else achieved < 95 % of target → *saturated*, degraded; else *comfortable*, ok. *Saturated* names the CPU when peak CPU ≥ 0.45 cores, else the pool when ≥ 100 wait. `n/a` = not measured (no two consecutive api stats samples got through while the api was being killed).

**What limits what**

1. Reads keep up on Kubernetes to 3000 rps with p99 9.1 ms at 0.23 cores and 0 throttled periods, the same shape as compose (p99 15.1 ms).
2. Read 5000 sits on the edge: the recorded pass held 4996.8 rps (p99 50.7 ms, 0.46 cores, 37 throttled periods); a first pass was OOM-killed twice (3517.9 rps, 17 809 dropped, 44 575 errors).
3. Writes are bounded by the pg pool of 10: write 1000 reaches 837.8 rps with 2883 waiting at 0.19 cores, the ~800 rps knee compose showed.
4. Past the write knee the api is OOM-killed twice per run (write 2000, 3000, 5000 and mixed 3000). Kubernetes restarts it within the run, so requests fail fast (p50 187.2 to 187.6 ms and max in flight 4497 to 4910 at write 2000, 3000 and mixed 3000, against 10 000 on compose) and achieved rps counts those failures: goodput is 272, 231 and 90 rps for write 2000, 3000, 5000 and 355 rps for mixed 3000.
5. Mixed 1000 is fine (p99 18.2 ms). Every error in the matrix has no HTTP status and falls in a run where the api was OOM-killed, so none is attributed to the NodePort path; the NodePort did reset connections for up to ~100 s after each kill while the pod was Ready, which is why runs were gated on clean health probes and why stats samples are missing in killed runs.

**Compared with compose** (`results/000-baseline.json`)

- Read 3000: 2997.3 rps, p99 9.1 ms on k8s vs 2998.9 rps, p99 15.1 ms on compose.
- Read 5000: 4996.8 rps, p99 50.7 ms, 0 dropped vs compose 3731.1 rps, 9051 dropped; a first k8s pass was OOM-killed (3517.9 rps), so 5000 is the edge on both.
- Write 1000: 837.8 rps with 2883 pool waiting vs 808.4 rps with 3865 waiting: the same pool-of-10 knee near 800 rps.
- Write 2000/3000/5000 and mixed 3000 are OOM-killed on both; k8s restarts the api mid-run (2 restarts each), so max in flight stays at 4497 to 10 000 and goodput at write 2000 is 272 rps vs compose's 984 achieved.
- Idle api memory is lower on k8s: 50.1 MiB peak at read 100 vs 110.0 MiB on compose.
